---
description: Draft a commit message or pull request based on current git state — semantic commits, concise, no attribution
---

Investigate the current working tree and branch state, then draft
either a commit message or a pull request depending on what's needed.

## Step 1: Assess git state

Run all of these in parallel:

1. **Working tree** — `git status --short` to see if there are
   uncommitted changes (staged or unstaged).

2. **Current branch** — `git branch --show-current` to get the branch
   name.

3. **Default branch** — `git rev-parse --abbrev-ref origin/HEAD` to
   find the remote default branch (e.g., `origin/main`). Fall back to
   `origin/main` if unset.

4. **Unpushed commits** — first check if an upstream is configured
   with `git rev-parse --abbrev-ref --symbolic-full-name @{u} 2>/dev/null`.
   If it returns a ref, compare with
   `git log <upstream-ref>..HEAD --oneline`. If no upstream is set,
   treat all commits diverged from the default branch as unpushed.
   Avoid using `@{upstream}` or `@{u}` directly in shell commands —
   the braces trigger sandbox permission prompts.

5. **Diff against default branch** —
   `git log --oneline <default-branch>..HEAD` for commit list, and
   `git diff <default-branch>...HEAD --stat` for a file-level summary.

From this, determine the mode:

- **Dirty tree** (uncommitted changes exist) → **Commit mode**
- **Clean tree, unpushed commits** → **Push + PR mode** (offer to push
  and open a PR)
- **Clean tree, all pushed** → **PR mode** (open a PR)
- **Clean tree, no diverged commits** → nothing to do, tell the user

## Step 2a: Commit mode

Study the uncommitted changes:

```bash
git diff          # unstaged changes
git diff --cached # staged changes
```

Draft a single-line commit message using
[Conventional Commits](https://www.conventionalcommits.org/):

- Format: `<type>: <short imperative description>`
- Types: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `ci`,
  `style`, `perf`, `build`
- Add a scope in parentheses when there's a clear module or area:
  `feat(auth): add token refresh`
- Keep under 72 characters
- No body, no footer, no co-authored-by

If changes span multiple unrelated concerns, draft separate commit
messages and suggest the user stage and commit incrementally.

**If on `main` or `master`**, check out a new branch before committing.
Derive the branch name from the drafted commit message: strip the type
prefix, lowercase, replace spaces with hyphens, drop punctuation.
Example: `feat(auth): add token refresh` → `feat/add-token-refresh`.

```bash
git checkout -b <branch-name>
```

Present the drafted message using the `AskUserQuestion` tool:

- Question: "Commit with this message?" with the drafted message shown
- Options: "Yes, commit" / "Edit message" (let the user type a
  replacement)
- If the user picks "Edit message", use their input as the commit
  message instead

On confirmation:

```bash
git add -A
git commit -m '<message>'
```

Then re-assess: if there are now unpushed commits and the branch is not
the default branch, continue to Step 2b.

## Step 2b: Push + PR mode

If unpushed commits exist, use the `AskUserQuestion` tool to offer to
push:

- Question: "Push to origin/<branch>?"
- Options: "Yes, push" / "No, skip"

On confirmation:

```bash
git push -u origin <branch>
```

If skipped, stop here — do not continue to Step 2c.

## Step 2c: PR mode

Study all commits diverged from the default branch:

```bash
git log --format='%h %s' <default-branch>..HEAD
git diff <default-branch>...HEAD
```

Also check for related issues:

```bash
git log --format='%B' <default-branch>..HEAD
```

Look for issue references in commit messages, branch name (e.g.,
`42-feature-name`), and the diff itself. Also query the repo:

```bash
gh issue list --state open --json number,title --limit 50
```

Match issues by topic, keywords, or explicit references.

Draft a pull request:

**Title** — single-line Conventional Commit format, same rules as
commit messages. Summarize the overall intent of the branch, not
individual commits.

**Body** — concise, factual, no filler. Structure:

```md
Resolves #<N>

## Summary

- <what changed, 1-3 bullet points>
```

Use `Resolves` for issues fully addressed, `Closes` for issues that
should auto-close. Omit the section entirely if no issues are related.

No attribution lines, no "Generated by" footers, no emoji.

Present the title and body using the `AskUserQuestion` tool:

- Question: "Create this PR?" with the title and body shown in the
  description
- Options: "Yes, create PR" / "Edit title" / "Skip"
- If the user picks "Edit title", use their input and ask again

On confirmation, pass the body inline. Use single quotes for both
`--title` and `--body` to avoid brace expansion prompts:

```bash
gh pr create --title '<title>' --body '<body>'
```

If the body contains single quotes, escape them as `'\''`.

Report the PR URL back to the user.

## Rules

- Never add `Co-Authored-By`, `Generated by`, or similar attribution.
- Never include a commit message body — single line only.
- PR descriptions must be factual and minimal — no narrative, no
  context the reviewer can get from the diff.
- If `gh` is not available, fall back to printing the PR title and body
  so the user can create it manually.
- If the branch has no upstream and `git push` fails, suggest the user
  set the upstream manually.
